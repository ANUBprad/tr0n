- Redis module (Redis 7.4+), property graph + OpenCypher, sparse-matrix
  engine; official clients incl. Go (`falkordb-go`, BSD) and `rueidis`.
- TRON delegates: storage, traversal, path queries, persistence.
- TRON keeps: provenance rules, layering, identity resolution, reasoning,
  answer synthesis.
- Interaction: bounded deliberate queries; evidence = returned paths;
  all Cypher confined to `internal/graph`.

## 4. Product definition (`docs/product-definition.md`)

Living organizational intelligence over relationships (people, teams,
projects, repos, services, documents, decisions, meetings, incidents, PRs,
technology). Answers with evidence chains, not vibes. New invariant:
never present inference/recommendation as fact.

## 5. Architecture conclusion (`docs/architecture-minimal.md`)

Thin clients → stateless Go API → five deterministic graph operations →
FalkorDB. Ingestion is the only fact writer; the future agent layer reads
operation output and never invents graph state. Core runs with no LLM and no
UI. Ten principles kept; "database abstraction" etc. challenged and dropped.

## 6–7. Technology candidates → recommended stack (`docs/technology-evaluation.md`)

Candidates: Go, Rust, TS, Python, Java/Kotlin, C# — all FalkorDB-capable.
**LOCKED: Go.** Requirement-by-requirement comparison over Rust: I/O-bound
workload shape, stdlib HTTP, `CGO_ENABLED=0` one-env-var cross-compilation,
iteration speed, one-dependency posture. Rust reserved for profiled hotspots
as separate processes (never cgo).

## 8. Graph model summary (`docs/GRAPH_MODEL.md`)

- **11 entities**: Person, Team, Project, Repository, Service, Document,
  Decision, Meeting, Incident, PullRequest, Technology — each with identity
  key (`src:native-id`), required/optional properties, native timestamps.
- **16 relationships**, all explicit facts, 4 temporal
  (`WORKS_IN`, `OWNS`, `WORKED_ON`, `DEPENDS_ON`… + `HAS_REPO`):
  WORKS_IN, OWNS, WORKED_ON, AUTHORED, REVIEWED, MODIFIED, HAS_REPO,
  DEPENDS_ON, AFFECTS, RESOLVED_BY, SUPPORTED_BY, DISCUSSED_IN,
  PARTICIPATED_IN, SUPERSEDES, ABOUT, USES.
- Cut: MEMBER_OF (dup), KNOWS (inference-as-fact), RELATED_TO (unfalsifiable),
  CAUSED, IMPLEMENTS, WORKED_ON→Service (double counting).
- Added: HAS_REPO (code→service bridge), ABOUT (doc subject), USES (tech).
- Deferred: System, Ticket, Conversation, Deployment, Organization — each
  with a stated reason.

## 9. Agent model summary (`docs/AGENT_SPEC.md`)

Boundary = 5 deterministic operations + ResolveEntity:
FindOwner, FindExperts, TraceDecision, FindRelatedIncidents, TraceEvidence.
Each documented with input/output/traversal/deterministic logic/provenance.
Deterministic core vs probabilistic edge enforced by contract: LLM (future)
selects and narrates only; `prepare_handoff` deferred as an agent-layer
composition; fuzzy `search_graph` dropped pending an embedding story.

## 10. MVP boundary

Five workflows unchanged (owner / experts / decision / history / routing),
each mappable to one operation; v1 core = operations + JSON API + seeded
graph — no LLM required to demonstrate the thesis.

## 11. Major risks

1. **Expertise weights are guesses until validated** — mitigated by
   versioned `expertise/v1`, basis paths visible, config-tunable.
2. **Identity resolution across sources unproven** — v1 single-source
   synthetic data; `aliases` designed but exercised late.
3. **Deliberate retrieval quality depends on op design** — bounded depth may
   miss far relationships; TraceEvidence + iterate is the recovery path.
4. **Go client choice (`falkordb-go` vs `rueidis`) uninspected** — deferred
   to scaffold with an explicit inspection step (OPEN_QUESTIONS).
5. **Hackathon-era docs coexist with locked docs** — banner on
   `ARCHITECTURE.md` resolves the contradiction; consolidation deferred.

## 13. Cross-platform strategy

Pure Go (`CGO_ENABLED=0`) cross-compiled to linux/macOS/windows ×
amd64/arm64; single static binary + distroless image; Docker-compose with
FalkorDB; API-first so all clients stay thin; local-first always works.

## 14. Security considerations

Single writer (ingestion) for facts; API/agent read-only on the graph; graph
name = future tenant boundary; no secrets in repo; env config; every claim
carries layer + provenance (auditable answers). Full enterprise authZ
explicitly not built yet.

## 15. Testing strategy

Real-FalkorDB-in-Docker operation tests with seeded fixtures; provenance
invariant tests (missing `src_*` = failure); layering tests (no inference
labeled fact); temporal supersession tests; ≥3-hop fixture tests (product
thesis as a test); ingestion idempotency/conflict tests; e2e smoke;
compile-only GOOS/GOARCH CI matrix. One check per non-trivial unit.

## 16. Performance considerations

Measure first: Cypher wide-pattern scans (bounded depth + `key`/`name`
indexes), expertise aggregation (single query; materialize only if
profiled), ingestion fan-out (bounded workers, per-source isolation), future
LLM latency (NL layer only), evidence payload size (small by design).
p50/p95 per operation; no optimization without numbers.
